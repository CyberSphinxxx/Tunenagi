## 1. The policy

`ProviderRetry` is the single bounded retry decision, driven by the existing taxonomy instead of by
a provider:

- **Bounded**: `maxAttempts` (default `ProviderError.MAX_ATTEMPTS = 3`) caps the calls. Backoff is
  `ProviderError.backoffFor(attempt, jitter)` — 500 ms, then 1 s, capped at 30 s.
- **`Retry-After` wins**: a `ProviderError.Throttled` with a `retryAfter` waits exactly that long
  instead of the exponential step. The transport already parses seconds *and* HTTP-dates.
- **Long waits are not taken**: a `Retry-After` above the 30 s budget is surfaced immediately. It
  stays `retryable` and keeps its value, so a caller may schedule a later attempt itself instead of
  the policy either hammering the provider early or freezing a screen.
- **Permanent refusals cost one request**: `Restricted` (`403`), `Unauthorized` (`401`), `NotFound`,
  `MalformedPayload` are not retried.
- **Cancellation propagates**: `ensureActive()` before every attempt and after every wait, and no
  `CancellationException` is caught. The injected sleeper exists only for tests; production uses
  `delay`, which is cancellable.

`sleeper` and `jitter` are constructor-injected so the schedule is asserted exactly rather than by
wall clock. `ProviderRetry.STANDARD` is the production value; `ProviderRetry.NONE` exists for a call
whose failure must be shown at once.

## 2. Integration

`AudiusApi.search` and `AudiusApi.trending` wrap their single page request in `retry.run { ... }`.
The constructor's default is `ProviderRetry.STANDARD`, so discovery recovers from a transient failure
without any caller opting in. Arg validation and the blank-query refusal happen before `run`, so a
bad argument still makes **zero** requests.

The stream resolver deliberately keeps **one attempt** per resolve: sleeping inside
`onAddMediaItems` would stall the player, and the provider's `Retry-After` is already surfaced in the
typed failure for the UI to act on (TUN-0305/TUN-0307). That is a product choice, not an omission, and
it is stated here rather than left implicit.

## 4. Gate correction found by this audit

The TUN-0303 commit passed its checks before committing and failed after, because the format and
boundary checks read the **Git index**: the new MockWebServer test was untracked during that run. With
the file committed, `verify.py` failed `format` (trailing blank line in `progress.md`, F3) and
`boundaries` (B11: `okhttp3.mockwebserver` imported from a `core.provider.*` package).

Both are fixed in this slice: the test moved to `core/src/test/java/com/tunenagi/core/network/` with
no assertion change (12 tests still pass), the progress file was trimmed, and
`OPERATIONS/GIT_CONVENTIONS.md` now says to stage before running the gates. The failing manifest is
kept: `STATE/evidence/TUN-0304/20261020T225119Z-verify-all-steps.json`.

This is recorded as a process defect, not a code defect: the product behaviour of TUN-0303 was
unaffected, but its "9/9 green" claim at commit time did not cover the committed test file.

## 5. Limitations (not hidden)

- **No live Audius request.** ADR-017 still holds; the `Retry-After` behaviour is proven against
  synthetic responses, not against a provider that actually throttles this client. TUN-0306 owns the
  live smoke.
- **No device proof.** ADR-008 deferral. The policy is a pure coroutine unit with an injected clock, so
  there is no runtime surface beyond the JVM tests.
- **The retry budget is a client policy, not a provider guarantee.** 3 attempts and a 30 s cap are the
  app's choices; the provider's plan limits (10 req/s, per ADR-017) are respected because a throttled
  response is never retried before its `Retry-After`.

## 6. Verdict

The slice delivers one bounded, cancellation-safe retry policy driven by the error taxonomy,
honouring `Retry-After`, refusing to retry permanent refusals, integrated into the real discovery
client and covered by deterministic failure-path tests. It also repairs the two gate violations the
previous commit introduced and closes the process hole that let them through.
